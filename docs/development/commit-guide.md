# Commit Guide

AI가 매번 따르는 짧은 규칙은 [AGENTS.md](../../AGENTS.md)에 있다. 이 문서는 상세
기준이다.

## 형식

```
<타입>(<스코프>): <제목>

<본문> (선택)
```

### 제목은 명사형으로 끝낸다

이슈·커밋·PR 제목은 `정리`, `추가`, `수정`, `개선`, `제거` 처럼 명사형으로
끝낸다. `정리한다`, `추가합니다` 같은 서술형은 쓰지 않는다. 본문은 자연스러운
문장으로 쓴다.

```text
# Good
feat(web): 프로젝트 목록 화면 추가
fix(db): crew 중복 참여 제약 수정

# Bad
feat(web): 프로젝트 목록 화면을 추가한다
fix(db): crew 중복 참여 제약을 수정합니다
```

## 스코프

| 스코프 | 대상                            | 예시                                 |
| ------ | ------------------------------- | ------------------------------------ |
| `root` | 루트 설정, CI, 스크립트, 의존성 | `chore(root): Vercel 배포 연결`      |
| `web`  | `src/` Next.js 앱               | `feat(web): 포스터 업로드 추가`      |
| `db`   | `supabase/` 스키마, 정책, 시드  | `feat(db): capers 테이블과 RLS 추가` |
| `docs` | `docs/`, README                 | `docs(docs): 미리보기 규칙 정리`     |
| `ios`  | `ios/` SwiftUI 앱(나중에)       | `feat(ios): 프로젝트 목록 화면 추가` |

## 타입

| 타입       | 설명                   | 예시                                            |
| ---------- | ---------------------- | ----------------------------------------------- |
| `feat`     | 새 기능                | `feat(web): 링크 공유 미리보기 이미지 추가`     |
| `fix`      | 버그 수정              | `fix(web): 긴 제목이 포스터를 가리는 문제 수정` |
| `refactor` | 동작이 같은 구조 개선  | `refactor(web): caper 조회를 entity로 분리`     |
| `style`    | 코드 포맷만            | `style(root): Prettier 적용`                    |
| `design`   | 화면 구조·여백·문구    | `design(web): 프로젝트 표지 여백 조정`          |
| `chore`    | 빌드, 설정, CI, 의존성 | `chore(root): husky와 lint-staged 추가`         |
| `docs`     | 문서                   | `docs(root): 작업 규칙 문서 추가`               |
| `test`     | 테스트                 | `test(web): caper 스키마 검증 테스트 추가`      |
| `release`  | 배포(dev → main)       | `release(root): dev → main 배포 (2026-11-01)`   |

### 타입 고르는 기준

작업의 최종 목적으로 고른다. 같은 화면 작업이어도 데이터 연결, 화면 구성, 오류
안내, 문서는 타입이 다르다.

| 상황                                           | 타입       |
| ---------------------------------------------- | ---------- |
| 새 route, Server Action, entity api, DB 테이블 | `feat`     |
| 잘못된 동작, 빠진 오류 처리, 잘못된 상태       | `fix`      |
| 화면 구조, 여백, 테두리, 버튼 크기, 문구 배치  | `design`   |
| 코드 포맷만 바뀜                               | `style`    |
| 구조만 바뀌고 동작과 화면은 같음               | `refactor` |
| 문서, 가이드                                   | `docs`     |
| 의존성, 빌드, CI, 설정                         | `chore`    |

`style` 은 CSS 작업이 아니라 코드 포맷이다. 화면을 만들거나 다듬는 작업은
`design` 이다.

## 지킬 것

- 하나의 커밋에는 하나의 목적만 둔다.
- 제목은 구체적으로 쓴다. `feat(web): 기능 추가`, `fix(web): 수정` 은 안 된다.
- 혼자 이해할 수 있고, 검증할 수 있고, 되돌릴 수 있는 단위로 커밋한다.
- 제목만으로 이유가 분명하지 않으면 본문에 쓴다.

## 하지 않을 것

- 여러 기능을 한 커밋에: `feat(web): 로그인, 참여, 저장 구현` → 셋으로 나눈다.
- 모호한 제목: `fix(web): 수정`, `refactor(root): 코드 정리`.
- WIP 커밋.
- 포맷과 로직을 한 커밋에. lint-staged가 staged 파일만 정리하는 것은 예외다.
- 스코프를 섞기: `db` 마이그레이션과 `web` 화면은 따로 커밋한다.
- 서명: `Co-Authored-By`, `Signed-off-by`, 생성 도구 문구.

## 단계별 커밋

단계별 커밋은 작업이 길어서가 아니라 되돌릴 수 있는 의미 단위가 생겼을 때
만든다. AI와 작업할 때는 변경이 커지기 전에 끊는다.

- 커밋 전에 변경 항목을 목록으로 적고, 로그에서 따라갈 수 있는 단위로 다시
  묶는다.
- 화면 구조, 데이터·상태 로직, 문서는 서로 다른 커밋이다.
- 같은 파일이어도 목적이 다르면 나눈다.
- DB 마이그레이션, entity api, Server Action, 화면, 오류 안내, 미리보기 케이스는
  따로 되돌릴 수 있으면 나눈다.
- 한 단위가 검증되면 다음으로 넘어가기 전에 커밋한다. `git diff --stat` 과 검증
  결과를 확인한다.
- 리뷰 반영도 성격별로 나눈다.

예: 프로젝트 만들기 기능

```
feat(db): capers 테이블과 RLS 추가
feat(web): caper 생성 Server Action 추가
design(web): 프로젝트 만들기 화면 구성
feat(web): 포스터 업로드 추가
fix(web): 포스터 업로드 실패 안내 추가
feat(web): 프로젝트 만들기 미리보기 케이스 추가
```

## 커밋 전 확인

- [ ] 목적이 하나다.
- [ ] 제목이 구체적이고 명사형으로 끝난다.
- [ ] 타입과 스코프가 맞다.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm build` 가 통과한다(앱이 생긴 뒤).
- [ ] 서명이 없다.
