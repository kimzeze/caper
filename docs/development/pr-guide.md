# PR Guide

PR의 목적은 리뷰하는 사람(나중의 나, AI 리뷰 포함)이 빠르고 정확하게 이해해서
merge까지 짧게 가는 것이다.

## 1. 원칙

| 원칙            | 요약                                                     |
| --------------- | -------------------------------------------------------- |
| **Small**       | 300 LOC 이하 권장. 400을 넘으면 나눌 수 있는지 본다.     |
| **Focused**     | PR 하나에 목적 하나. 리팩토링, 기능, 포맷을 섞지 않는다. |
| **Descriptive** | 제목으로 의도가, 본문으로 맥락이 보인다.                 |
| **Testable**    | 검증 절차, 스크린샷, 영향 범위를 적는다.                 |
| **Reviewable**  | push 전에 자기 diff를 한 번 본다.                        |

## 2. 크기

| 변경량  | 판단 | 할 일                                          |
| ------- | ---- | ---------------------------------------------- |
| ~100    | 좋음 |                                                |
| 100~300 | 보통 |                                                |
| 300~500 | 주의 | 나눌 수 있으면 나누고, 못 나누면 이유를 적는다 |
| 500+    | 위험 | 거의 늘 나눈다                                 |

나누는 방법:

1. 선행 리팩토링 PR을 먼저, 기능 PR을 그 위에.
2. 공통 컴포넌트·유틸 PR을 먼저, 쓰는 곳 PR을 다음에.
3. DB 스키마 → entity api → 화면 순.
4. 기능을 작은 사용자 가치 단위로 자르기(만들기만, 그다음 보기).

떨어질 수 없는 변경(함수 시그니처와 모든 호출처)은 묶는다.

## 3. 제목

```
<type>(<scope>): <한글 제목>
```

- 형식은 [Commit Guide](./commit-guide.md)와 같다. 70자 안쪽.
- `PR Title Check` 가 형식을 검사한다.
- WIP는 제목 대신 Draft PR로 표시한다.

## 4. 본문

`.github/pull_request_template.md` 가 채워진다.

- **관련 이슈:** `closes #N`. 닫지 않는 관련 이슈는 `related: #M`.
- **문제 / 배경:** 무엇을 바꿨는지보다 어떤 문제를 풀었는지 먼저.
- **검토한 대안:** 방법이 둘 이상이면 대안과 고르지 않은 이유. 없으면 "대안
  없음, 단순 수정"처럼 적는다.
- **선택한 해결 방식:** 어떻게 풀었고 왜 이 방식인지. 리뷰 중 고친 엣지케이스도
  여기에.
- **변경 요약:** 3~5문장.
- **검증 방법:** 따라 할 수 있는 절차. 명령, 주소, 누를 곳.
- **영향 범위:** 바뀐 화면, DB 변경 여부, 호환성.
- **스크린샷:** UI 변경이면 필수. 390px 먼저, 필요하면 1280px과 다크 모드.

## 5. 리뷰 코멘트 반영

리뷰 코멘트는 고치라는 명령이 아니라 검토할 입력이다. 리뷰 봇은 맥락을 놓칠 수
있다.

바로 반영해도 되는 것: 오타, 포맷, import 정렬, 명백한 타입·lint 오류, CI가
가리킨 의존성 보안 패치, 이미 합의한 범위 안의 단순 누락.

판단이 필요한 것: 인증, 권한(RLS), 데이터 계약, 캐시와 재검증, 공통 컴포넌트,
폴더 구조와 import 경계. 이때는 먼저 이슈나 PR에 남긴다.

```markdown
## 리뷰 코멘트 검토

- 리뷰 내용:
- 분류: 버그 / 보안 / 설계 의견 / 나중에 처리 / 오탐
- A안:
- B안:
- 추천:
- 선택:
- 검증:
```

## 6. 피할 것

| 안티패턴               | 문제                                    |
| ---------------------- | --------------------------------------- |
| 1000+ LOC 단일 PR      | 리뷰 품질이 떨어지고 회귀를 찾기 어렵다 |
| 제목만 있고 본문 없음  | 맥락을 추측하게 된다                    |
| `closes #N` 누락       | merge 뒤 이슈가 열린 채로 남는다        |
| 스크린샷 없는 UI PR    | 직접 띄워 봐야 해서 사이클이 길어진다   |
| 검사 실패 상태로 리뷰  | 리뷰 시간이 버려진다                    |
| merge 직전 무관한 변경 | 앞선 리뷰가 무효가 된다. 새 PR로 뺀다   |

## 7. 자주 묻는 것

- **나누기 어려운 큰 변경:** 본문 첫 줄에 나누지 못한 이유를 적는다.
- **PR을 연 뒤 고칠 것을 찾으면:** 추가 커밋을 쌓는다. 리뷰 전이면 force push도
  괜찮다.
- **충돌:** `git fetch && git rebase origin/dev` 또는 `git merge origin/dev`.
